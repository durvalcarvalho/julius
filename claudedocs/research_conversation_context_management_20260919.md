# Memória de conversa e pergunta pendente — como o problema já foi resolvido fora daqui

Pesquisa feita em 2026-09-19. Escopo: só pesquisa/recomendação, nenhum código alterado nem arquitetura decidida — aplica-se às três lacunas abertas em `docs/requirements/shopping-list-conversation-context.md` (RF4: responder "sim" à luz da pergunta anterior do bot; RF5: acumular itens ao longo de várias mensagens; RF6: lembrar assunto fora da janela atual de `HISTORY_TURNS = 3`).

Boa notícia adiantada, confirmando o que o usuário suspeitava: **nada disto é fronteira de pesquisa**. É um problema resolvido desde os anos 1970–80 (sistemas de frame/slot como o GUS da Xerox PARC) e reempacotado hoje pela indústria de chatbot/LLM sob nomes como "dialogue state tracking" e "memória de agente". A dificuldade real deste projeto não é achar a técnica — é escolher a versão proporcional a um bot de um usuário só com orçamento de US$5/mês, sem reintroduzir a "busca semântica desproporcional" que o projeto já rejeitou para outra coisa.

## 1. RF4 — Responder "sim" à luz da pergunta anterior: dialogue state tracking / slot filling

O padrão chama-se **dialogue state tracking (DST)**: o sistema mantém um registro do que já foi perguntado e do que ainda falta, turno a turno, e usa esse registro — não só o texto cru — para decidir se a mensagem nova é resposta a algo pendente ou um assunto novo ([usefini.com](https://www.usefini.com/glossary/what-is-dialogue-state-tracking-dst); [Tencent Cloud](https://www.tencentcloud.com/techpedia/127699)). A peça concreta que resolve o caso "sim" é mais simples que DST completo: é o conceito de **slot filling com forms** do Rasa (clássico, pré-LLM, sem nenhuma rede neural obrigatória) — "se você precisa de uma informação específica pra continuar, o sistema pergunta e trava numa etapa de 'aguardando resposta a X' até a receber" ([Rasa forms](https://medium.com/rasa-blog/building-contextual-assistants-with-rasa-forms-7c034c9a8677); [Rasa slot filling docs](https://legacy-docs.rasa.com/docs/core/slotfilling/)). A literatura recente sobre agentes clarificadores generaliza a mesma ideia para LLM: "quando o sistema faz uma pergunta de esclarecimento, a próxima entrada do usuário deve ser interpretada no contexto dessa pergunta, não como uma nova mensagem solta" ([Clarifying Agent survey](https://www.emergentmind.com/topics/clarifying-agent); [First Ask Then Answer](https://arxiv.org/html/2508.08308v1)).

**O que isso significa em termos concretos, sem prescrever schema**: o registro de "pergunta pendente" precisa ser um **dado explícito**, não uma esperança de que o modelo religue os pontos sozinho olhando o histórico bruto. Isso não é novidade nenhuma para este projeto — é exatamente a mesma forma que `PendingWrite` já usa para escrita (grava o que está em aberto, o próximo turno consome aquele estado antes de decidir agir do zero). A diferença é só que hoje esse mecanismo existe apenas para o caminho de escrita; a pesquisa aponta que o caminho de leitura/conversa precisa da mesma peça, versão mais simples (não precisa de confirmação por botão, só de "o que eu perguntei" persistido entre o fim de um turno e o começo do outro).

## 2. RF5 — Acumular itens ao longo de várias mensagens: já parcialmente coberto pelo que existe

A forma mais básica de memória de chatbot com LLM, confirmada por toda a literatura de 2025–2026, é literalmente **"mandar as últimas N mensagens no prompt"** — é isso que a maioria dos sistemas reais faz primeiro, e funciona bem para conversas curtas ([Medium, Beyond Chat History](https://medium.com/@fayzanpopatiya/beyond-chat-history-modern-strategies-for-long-term-memory-in-llms-0cdc9f7634f7); [mem0 blog](https://mem0.ai/blog/llm-chat-history-summarization-guide-2025)). Isso é exatamente o que `HISTORY_TURNS = 3` já faz. Ou seja: **"preciso de leite" → "e pão" → "qual mercado?" já deveria funcionar hoje**, contanto que as três mensagens caibam dentro da janela de 3 turnos — o requisito RF5 provavelmente já está resolvido pelo mecanismo existente, e o que falta não é código novo, é reforçar no prompt que o modelo deve **somar** menções de produtos das mensagens recentes em vez de responder só com base na última linha (o mesmo achado de "acúmulo entre turnos" que a literatura de slot filling chama de merge de slot-value, não substituição — ver seção 1). Vale medir isso separadamente antes de assumir que precisa de mecanismo novo.

## 3. RF6 — Lembrar além da janela atual: as três famílias de solução, e por que "extração" é a proporcional aqui

Toda a literatura converge em três famílias, cada uma com o trade-off medido:

**(a) Janela deslizante maior (sliding window)** — só aumentar `HISTORY_TURNS`. Barato, zero peça nova, mas "descarta decisões antigas e mantém conteúdo recente de baixo valor" de forma imprevisível — o problema não desaparece, só empurra a fronteira ([arXiv 2606.11213, Structured Context Eviction](https://arxiv.org/pdf/2606.11213)). Custo: tokens de entrada crescem linear com N, e este projeto já paga por token de entrada (a chamada mais cara hoje, 2140–2584 tokens de entrada, é dominada pelo prompt+schema das ações, não pelo histórico — mas aumentar N soma em cima disso).

**(b) Sumarização/compactação (o que o LangChain chama de `ConversationSummaryBufferMemory`)** — quando a janela enche, as mensagens mais antigas são resumidas por uma chamada de LLM e substituídas por um resumo curto, mantendo as recentes em texto cru ([LangChain docs](https://python.langchain.com/api_reference/langchain/memory/langchain.memory.summary_buffer.ConversationSummaryBufferMemory.html); [Neural Base](https://theneuralbase.com/langchain-advanced/learn/intermediate/hybrid-summary-buffer/)). Funciona, mas tem uma patologia documentada: **"summarization drift"** — cada resumo perde detalhes de baixa frequência, e depois de várias rodadas o agente "lembra" uma versão genérica e sanitizada do histórico, que falha exatamente nos casos de borda (arXiv, [Beyond Compaction](https://arxiv.org/pdf/2606.11213)). Custo: uma chamada de IA extra a cada estouro de janela — orçamento a medir (RNF2 do requisito).

**(c) Extração de fatos discretos, não resumo em prosa** — a tendência mais recente (2026) é abandonar resumo textual e extrair **fatos pontuais, estruturados e atualizáveis** ("lista atual: leite, pão"; "mercado preferido: X") guardados como registros, não como parágrafo. A justificativa medida pela própria mem0: resumo é lossy e não permite atualizar um fato isolado sem reprocessar tudo; extração guarda unidades pequenas que podem ser sobrescritas uma a uma ([mem0, LLM Summarization Techniques 2026](https://mem0.ai/blog/llm-chat-history-summarization-guide-2025); [mem0, State of AI Agent Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)).

**Por que (c) é a proporcional aqui, e por que isso não é o mesmo erro que a busca semântica rejeitada.** Frameworks como Mem0/Zep/Letta implementam extração **com recuperação semântica via vetores**, porque foram desenhados para agentes com milhares de fatos e múltiplos usuários — exatamente o cenário que este projeto já mediu e recusou para busca de produto (catálogo pequeno, um usuário, sem ganho real de embeddings). Mas o **conceito** de extração (guardar 2–3 campos estruturados — "lista corrente", "pergunta pendente" — em vez de um resumo em prosa ou uma janela cega) não depende de vetor nenhum quando o número de fatos por usuário é pequeno e enumerável, que é exatamente este caso (uma pessoa, uma lista de compras por vez). Ou seja: **o padrão vale, a infraestrutura pesada que normalmente vem junto não é necessária aqui** — o equivalente proporcional é uma tabela SQLite pequena com campos nomeados (o mesmo estilo de `PendingWrite`/`ai_usage`), não uma nova dependência.

## 4. O que a pesquisa não decide (fica para `/sc:design`)

- Se RF6 precisa de (b) sumarização, (c) extração estruturada, ou simplesmente aumentar (a) a janela e medir se resolve a maioria dos casos reais primeiro — a mesma disciplina de "medir antes de argumentar" que já rege o projeto.
- Onde essa peça mora na DAG de camadas (`domain`/`infra`/`services`/`bot`) e como ela convive com `ChatState` (hoje em memória de processo, não persistido) — decisão de arquitetura, fora do escopo desta pesquisa.
- O texto exato de como o "estado pendente" de leitura se parece com — ou diverge de — `PendingWrite`, que hoje só existe para escrita.

## Recomendação (proporcional, não prescritiva)

Nenhum framework de memória (Mem0, Zep, Letta) se justifica pelo volume real deste projeto — mesma conclusão que já valeu para embeddings/FTS5/Alembic no CLAUDE.md. As três lacunas têm equivalentes baratos, sem dependência nova:

1. **RF4** — copiar a forma do `PendingWrite`: um campo explícito de "o que o bot perguntou por último" no estado do chat, consultado no próximo turno antes de tratar a mensagem como nova.
2. **RF5** — provavelmente já funciona dentro da janela de 3 turnos; medir antes de construir algo novo.
3. **RF6** — se a medição mostrar que 3 turnos não bastam na prática, a extração de fatos discretos (uma linha "lista corrente"/"pergunta pendente" por chat, em SQLite) é mais barata e mais confiável que sumarização em prosa (evita a "summarization drift" documentada) e não exige busca vetorial nenhuma.

Nada disto foi implementado ou decidido como arquitetura final nesta sessão — é insumo para o `/sc:design`.
