# Design de conversa, modelagem de dados, Telegram e DeepSeek — o que mudou e o que se aplica

Complementa `research_conversation_context_management_20260919.md` (mesma sessão, mesma origem: `docs/requirements/shopping-list-conversation-context.md`). Aquele relatório cobriu os padrões gerais de dialogue state tracking/memória de agente; este aprofunda quatro eixos que ficaram de fora: modelagem de dados concreta, mecanismos nativos do Telegram e do `python-telegram-bot`, o que mudou na API da DeepSeek especificamente, e isolamento por conversa. Só pesquisa — nenhum código foi alterado, nenhuma arquitetura foi decidida.

## 1. Modelagem de dados para conversas (SQLite puro, sem ORM)

O padrão que aparece consistentemente em exemplos reais (blogs técnicos, migrações de projetos abertos) separa três entidades: **conversa/sessão**, **mensagem** e **estado derivado** — nunca uma tabela só. Uma tabela `chat_conversations` (id, referência ao usuário/chat, timestamps) e uma `chat_messages` (id, `conversation_id`, `role`, `content`, timestamps), com índice em `conversation_id` por ser a query mais frequente ([dev.to — Persistent Chat History with Database Design](https://dev.to/masteringbackend/persistent-chat-history-with-database-design-practical-example-33da)). Isso é exatamente a forma de `prices`/`stores`/`products` já existentes no projeto — nenhuma novidade estrutural, só um agregado novo.

O achado mais direto para as lacunas RF4/RF5 vem da literatura de *dialogue state tracking*: tratar cada turno como uma **atualização incremental de um "belief state"**, não uma reconstrução do zero. O paper "Large Language Models as Zero-shot Dialogue State Tracker through Function Calling" ([arXiv:2402.10466](https://arxiv.org/pdf/2402.10466)) formaliza isso: cada domínio vira uma função, os slots são os argumentos, e — ponto central — **o modelo só precisa gerar o que mudou naquele turno** ("minimal update approach"); o código acumula o estado global a partir dos deltas. Isso mapeia direto no que o projeto já faz para escrita: `PendingWrite` já é "o código guarda um estado pendente entre dois turnos, resolvido por uma ação futura" — o mesmo desenho, aplicado a leitura/conversa, é uma tabela pequena tipo `pending_question(chat_id, kind, asked_at, details)` ou `conversation_intent(chat_id, items_json, updated_at)`, populada por uma *tool call* explícita do modelo em vez de o texto livre carregar tudo. Isso é modelagem de dados nova, mas do tamanho de uma migração `.sql` a mais — não uma tabela de fatos genérica nem busca vetorial.

## 2. Mecanismos nativos do Telegram e do `python-telegram-bot`

**`BasePersistence`/`PicklePersistence`/`context.chat_data`/`context.user_data`** — o framework já resolve "guardar um dicionário por chat que sobrevive a reinício", sem escrever SQL: basta construir a `Application` com um objeto de persistência, e `chat_data`/`user_data`/`bot_data` passam a ser salvos automaticamente ([wiki oficial — Making your bot persistent](https://github.com/python-telegram-bot/python-telegram-bot-wiki/wiki/Making-your-bot-persistent); [`BasePersistence` docs](https://docs.python-telegram-bot.org/en/stable/telegram.ext.basepersistence.html)). `PicklePersistence` é a implementação pronta (arquivo `.pickle` local); para não abrir um segundo arquivo de estado ao lado de `prices.db`, dá para implementar uma `BasePersistence` própria sobre o SQLite existente — o framework já prevê isso como o caminho para "manter conexão de banco própria" (mesma doc). **Trade-off real**: isso introduz uma segunda forma de estado (a API de persistência do PTB, com seu próprio ciclo de vida) rodando ao lado do banco que os `services/` já leem — vale medir se compensa versus só usar a tabela SQLite que o projeto já sabe migrar/testar.

**`ConversationHandler`** — a peça do PTB para diálogos multi-etapa (estados nomeados, transições por handler, opcionalmente persistente com `persistent=True, name=...`) ([issue #385](https://github.com/python-telegram-bot/python-telegram-bot/issues/385); docs de `BasePersistence`). **Tensão de arquitetura a registrar**: o design do bot (v2.6, `CLAUDE.md`) decidiu deliberadamente que **quem roteia é a IA** — cada mensagem escolhe uma entre catorze ações de um menu fechado, código executa. `ConversationHandler` é o oposto disso: um fluxo determinístico de estados definido em código Python, characteristic de bots sem IA de roteamento. Adotá-lo agora significaria duas máquinas de decisão convivendo (a IA escolhendo ação livremente, e um `ConversationHandler` também controlando "em que passo da conversa estamos") — provável fonte de conflito, não only mais uma peça bonita para eventual `/sc:design` decidir.

**`reply_to_message_id` / tópicos de fórum / `message_thread_id`** — API nativa para ligar uma resposta a uma mensagem específica ou isolar uma conversa por tópico dentro de um grupo ([Telegram Bot API](https://core.telegram.org/bots/api); exemplo de uso: [issue do spynel sobre `message_thread_id`](https://github.com/agent0ai/spynel/issues/7)). É o mecanismo "de graça" mais próximo de resolver RF4 (ligar a resposta do usuário à pergunta do bot) — mas depende do **usuário** usar o recurso "responder a" do Telegram, o que ninguém faz por hábito num chat 1:1 comum; não dá para depender disso como mecanismo primário, só como sinal opcional adicional quando presente. Tópicos de fórum (`message_thread_id`) são para grupos com múltiplas discussões paralelas — sem uso aqui, chat é 1:1.

**`aiogram` (FSM nativo)** — só como ponto de comparação, não como sugestão de troca de biblioteca: resolve o mesmo problema que `ConversationHandler` (estados nomeados, armazenamento plugável — memória, Redis, Mongo) ([docs oficiais de FSM do aiogram](https://docs.aiogram.dev/en/latest/dispatcher/finite_state_machine/index.html)). Mesma tensão de arquitetura do item anterior se fosse adotado o padrão equivalente.

## 3. LLM/DeepSeek — o que mudou e por que importa para o problema

**Nomes de modelo mudaram, mas o que o projeto configura continua válido.** `deepseek-chat`/`deepseek-reasoner` foram aposentados em 24/07/2026; hoje `deepseek-flash` é o alias recomendado e resolve para o DeepSeek-V4.1-Flash atual, com aliases legados (`deepseek-v4-flash`) ainda aceitos e roteados para o mesmo modelo ([DeepSeek API — model list, via busca]; [tech-insider.org — How to Use DeepSeek V4.1 Flash API](https://tech-insider.org/how-to-use-deepseek-v4-1-flash-api-2026/)). `JULIUS_AI_MODEL=deepseek-flash` do projeto **continua correto** sem mudança nenhuma.

**Janela de contexto saltou para 1 milhão de tokens** (V4.1 Flash e V4-Pro), com até 384 mil tokens de saída ([theneuralbase.com — DeepSeek context window comparison](https://theneuralbase.com/deepseek/qna/deepseek-context-window-comparison/); [deepseek-online.org](https://deepseek-online.org/)). Isso muda o cálculo por trás do `HISTORY_TURNS = 3`: o corte atual nunca foi sobre limite físico do modelo (nem perto), foi sobre custo e sobre não afogar a narração da persona em fatos demais (mesmo raciocínio que já limita `NARRATE_MAX_GROUPS`). Um histórico maior é tecnicamente trivial agora — a pergunta que sobra é só de custo e de qualidade de resposta (contexto muito longo tende a diluir atenção do modelo nas partes do meio, fenômeno bem documentado na literatura de LLM em geral, independente de fornecedor — vale medir, não assumir).

**Context Caching on Disk muda a conta de custo do "reenviar histórico".** Confirmado direto na documentação oficial ([DeepSeek API Docs — Context Caching announcement](https://api-docs.deepseek.com/news/news0802/)): o cache é automático, sem mudança de código, identificado por **prefixo idêntico a partir do token 0** — só bate cache se o início da entrada for byte-a-byte igual ao de uma chamada anterior recente; qualquer mudança no meio (reescrever uma mensagem antiga, reordenar) invalida tudo a partir dali. Entradas não usadas são limpas depois de horas a dias. O desconto é grande (os números variam por fonte/modelo pesquisada — uma cita ~90% de desconto no cache hit para V4-Pro, outra cita cache a **$0,003–0,014 por milhão** contra **$0,14–0,15 por milhão** de miss para V4.1 Flash; tratar como "desconto de uma ordem de grandeza", não fixar um número exato sem checar a fatura real). **Implicação prática direta para RF5/RF6**: se o histórico reenviado a cada turno for sempre um **prefixo estável e crescente** (mesmo system prompt + mesmas mensagens antigas, só anexando as novas no fim — exatamente como `state.history` já funciona hoje), a maior parte desse texto vira cache hit e custa uma fração do preço cheio. Isso enfraquece a suposição de que "aumentar `HISTORY_TURNS`/mandar mais contexto multiplica o custo linear" — vale medir com `ai_calls.jsonl` antes de rejeitar um histórico maior por custo (mesma disciplina de "medir antes de argumentar" já registrada no projeto).

**A API é 100% stateless — isso é responsabilidade do projeto, não do provedor.** Confirmado: `/chat/completions` da DeepSeek não guarda nada entre chamadas; ao contrário da Assistants API da OpenAI (que tinha `thread_id`), aqui **não existe** id de conversa no servidor — quem quiser lembrar de algo entre chamadas reenvia tudo, sempre ([serpapi.com — Multiround conversation with DeepSeek API](https://serpapi.com/blog/multiround-conversation-with-deepseek-api-ai-assistant/); [DeepSeek API Docs — Multi-round Conversation](https://api-docs.deepseek.com/guides/multi_round_chat/)). Isso fecha a dúvida: "gerenciar a conversa" é e continua sendo trabalho do código do Julius, nenhuma feature nova do provedor tira essa responsabilidade.

**`pydantic_ai` (já usado pelo projeto) tem persistência de mensagens embutida.** Achado que vale checar antes de desenhar algo do zero: o harness do próprio `pydantic_ai` oferece `StepPersistence` com backends `memory`/`file`/`sqlite`/`mongo` — `backend='sqlite'` grava o histórico de mensagens num arquivo SQLite de forma pronta, sem código de serialização manual ([Pydantic Docs — Step Persistence](https://pydantic.dev/docs/ai/harness/step-persistence/)). Isso é "dependência já instalada resolve" (o projeto já depende de `pydantic_ai` para o agente do bot) — precisa confirmar em `/sc:design` se essa API está disponível na versão já usada pelo projeto e se o arquivo SQLite dela pode ser o mesmo `prices.db` (a doc cita um `database` próprio, possivelmente um arquivo separado) antes de decidir usar.

**Function calling como mecanismo de estado explícito, não só JSON de resposta.** O padrão "DST via function calling" (seção 1) é a aplicação direta disso: em vez de pedir para o modelo re-interpretar todo o texto cru a cada turno, dar a ele uma ferramenta tipo `update_shopping_intent(items, answers_pending_question)` que só emite o que mudou. Isso é o mesmo mecanismo de *output functions* que o bot já usa para as catorze ações (`ALL_ACTIONS` em `bot/agent.py`) — não é uma técnica nova para o projeto, é a mesma técnica aplicada a um problema diferente (estado de conversa em vez de execução de comando).

**Padrões de memória de agente 2025-2026 (Mem0 e afins) confirmam a direção, mas a escala não se aplica.** Frameworks como Mem0 tratam extração de fatos + decisão ADD/UPDATE/DELETE/NOOP como uma chamada de ferramenta do próprio modelo, com recuperação por busca vetorial ([mem0.ai — State of AI Agent Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026); [machinelearningmastery.com — 5 Architectural Patterns for Persistent Memory and State in AI Agents](https://machinelearningmastery.com/5-architectural-patterns-for-persistent-memory-and-state-in-ai-agents/)). O **padrão** (fatos pequenos, decisão explícita de add/update via tool call) é reaproveitável; a **infraestrutura** (banco vetorial, embeddings) não se justifica para um catálogo de centenas de produtos e um usuário só — mesma conclusão já registrada no relatório anterior e coerente com a recusa histórica do projeto a embeddings/FTS5 por desproporção.

## 4. Uma ou várias conversas

O Julius é hoje explicitamente single-user (`JULIUS_BOT_ALLOWED_CHAT_ID`, allowlist de um `chat_id` só, `CLAUDE.md` v2.6) — isolar contexto por conversa, se algum dia o requisito mudar, é o padrão universal já visto na seção 1: chave composta `(chat_id, ...)` em vez de uma tabela global. Não é uma lacuna aberta hoje, só conhecimento de contexto para não fechar a porta sem querer.

## Recomendação (proporcional, decisão final é do `/sc:design`)

1. **Medir antes de mexer no tamanho do histórico.** Com contexto de 1M tokens e cache de disco por prefixo estável, aumentar `HISTORY_TURNS` (ou até manter a sessão inteira) pode já custar muito menos do que a intuição de "custo linear" sugere — checar `ai_calls.jsonl` (tokens de cache hit vs miss, se a API expuser isso na resposta) antes de assumir que precisa de mecanismo novo para RF5/parte de RF6.
2. **Para RF4/RF5, o mecanismo proporcional é uma *tool call* de atualização de estado**, no mesmo espírito de `PendingWrite` e das catorze ações já existentes — não um mecanismo do PTB (`ConversationHandler`/persistência própria), que entraria em tensão com o desenho "IA roteia, código executa" já decidido.
3. **`pydantic_ai.StepPersistence(backend='sqlite')` merece um olhar antes de desenhar uma tabela do zero** — é dependência já presente no projeto; se servir, é a opção mais barata da escada (ladder) de "já instalado resolve".
4. **Para RF6 (lembrar além da janela), nada de banco vetorial/Mem0** — desproporcional à escala (um usuário, algumas dezenas de mensagens por mês). Se sobrar necessidade depois de 1–3, uma tabela pequena de fatos (sujeito, valor, quando) alimentada pela mesma tool call do item 2 é o próximo degrau, não o primeiro.
